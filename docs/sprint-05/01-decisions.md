# Sprint 05: журнал решений

Статус: **GENERAL ARCHITECTURE AUDIT COMPLETE**. Ниже перечислены подтверждённые решения 1–38.
Рабочие шаги и проверки находятся в [плане frontend-задач](./02-frontend-task-breakdown.md).

### Решение 1. Адрес и показ поста

`/posts/[postId]` — канонический публичный адрес. Прямой переход показывает самостоятельную
SSR-страницу, а переход из Main или Profile — тот же пост в перехваченном маршруте `@modal`.
Маршрутизация через `?postId=` не используется.

### Решение 2. Свежесть публичных данных

Public Profile и Post формируются заново для каждого запроса. Сервер использует raw GraphQL
`fetch` с `cache: 'no-store'` и не создаёт Apollo Client. Авторизационные данные в публичный
запрос не передаются.

### Решение 3. Продолжение работы через Apollo Client

Серверные данные передаются сериализуемыми props и записываются через `writeQuery` в существующий
Apollo Client. Запросы должны содержать нужные `id` и `__typename`, а их поля и переменные — быть
совместимыми с последующим чтением из кэша.
Второй начальный запрос и новый слой данных не добавляются.

### Решение 4. Атомарная загрузка профиля

`InitialProfileData` содержит пользователя, публичные счётчики, первую страницу постов и
`baselineKey`. Данные отображаются и записываются в Apollo только полным набором.
Отсутствующий пользователь вызывает `notFound()`, остальные сбои считаются технической ошибкой.

### Решение 5. Базовая версия и пагинация профиля

Сервер создаёт `baselineKey` через `crypto.randomUUID()`. Новый пользователь или
`router.refresh()` сбрасывает локальную историю страниц; polling и `fetchMore` её сохраняют.
Пагинация остаётся локальной, без общего `typePolicy` или нового менеджера.

### Решение 6. Polling профиля

После записи начальных данных запрос постов использует `cache-first` и
`pollInterval: 60_000`; до этого действует `skipToken`. Ошибка polling не скрывает профиль,
а повтор выполняется через `refetch()`. Дополнительный контроллер polling не нужен.

### Решение 7. Публичные и пользовательские данные профиля

SSR должен содержать `publicationsCount`, `followersCount` и `followingCount`.
`isFollowing`, разрешённые действия и другие данные текущего пользователя остаются на клиенте.
Счётчик публикаций нельзя вычислять по первой странице постов.

### Решение 8. Данные публичного поста

В Sprint 05 пост использует только доступные author, attachments/media, description и
`createdAt`. Comments, replies, likes, счётчики и действия отмечаются как
`design-visible / contract-unavailable`; временные поля и фиктивные данные запрещены.

### Решение 9. Отсутствующий пост и ошибки

Для канонического маршрута отсутствующий пост вызывает `notFound()`; в перехваченном маршруте
показывается локальное сообщение о недоступности. Технические ошибки не превращаются в 404 и
обрабатываются в границах соответствующего маршрута.

### Решение 10. Закрытие и удаление поста

Перехваченный пост закрывается через `router.back()`. Самостоятельная страница закрывается
переходом в `/profile/[ownerId]`. Очищенный `returnTo` допустим только как запасной путь, а
удаление использует правила текущего способа показа.

### Решение 11. Источник данных открытого поста

Пост записывается в Apollo через `postQuery`, но отображается из серверных props и локального
`displayPost`. Успешное редактирование обновляет локальные данные и нормализованный кэш одним
ответом мутации; отдельный `useQuery(postQuery)` и повторный запрос не нужны.

### Решение 12. Базовая версия поста

Один успешный серверный запрос создаёт сериализуемый `baselineKey` через
`crypto.randomUUID()`. Новый маршрут или `router.refresh()` сбрасывает локальное состояние.
`updatedAt` не используется как версия без подтверждённого backend-контракта.

### Решение 13. Граница интеграции Edit Profile и Avatar

Изолированные UI, состояние и тесты можно делать до готовности backend. Рабочий маршрут
`/settings/profile` остаётся заглушкой до появления операций чтения и сохранения.
Временные GraphQL-операции и имитация успешного сохранения запрещены.

### Решение 14. Privacy Policy

Ссылка из ошибки возраста открывает существующий `DocModal`, не размонтируя форму.
Отдельный маршрут, глобальное хранилище и сериализация состояния формы не нужны.

### Решение 15. Уход с несохранённой формы

Sprint 05 не блокирует переход со страницы с изменённым Edit Profile. `beforeunload`,
`popstate`, перехват Link/router и общая система предупреждений не добавляются.

### Решение 16. Минимальная архитектура

Используются существующие возможности Next.js, Apollo, React и проекта. Новая абстракция допустима
только при реальном повторении или отдельной ответственности за состояние. Несвязанные рефакторинги
в Sprint 05 не входят.

### Решение 17. Независимость Edit Profile и Avatar

`EditProfileForm` владеет полями и RHF-состоянием, Avatar — выбором, crop и своими операциями.
Сохранение одной возможности не меняет состояние другой. Settings только компонует их и не создаёт
общую транзакцию или координатор.

### Решение 18. Форма crop аватара

Crop всегда квадратный `1:1`; круг используется только как маска отображения. Zoom, rotation,
прозрачные углы и физически круглый файл не добавляются. Итоговые размеры и кодирование зависят от
backend-контракта.

### Решение 19. Результат crop аватара

`AvatarCropSelection` содержит исходный `File` и квадратные `left/top/width/height`.
Координаты относятся к orientation-normalized decoded bitmap. Blob, canvas, object URL,
cropper refs, параметры загрузки и код Create Post наружу не передаются.

### Решение 20. Проверка файла аватара

Разрешены точные MIME `image/jpeg` и `image/png`, размер — не более `10 * 1024 * 1024` байт.
Сначала проверяется формат, затем размер; `accept` остаётся подсказкой file picker.
Ошибочная замена не уничтожает предыдущий корректный черновик.

### Решение 21. Дата рождения и возраст

Дата рождения имеет тип `Date | null` и необязательна. Дата из будущего запрещена, минимальный
возраст — 13 лет по календарным году, месяцу и дню. Сериализация, timezone и backend errors
определяются после проверки контракта.

### Решение 22. Проверка полей Edit Profile

Username: обязательно, 6–30, латиница, цифры, `_`, `-`. First/Last Name: обязательно, 1–50,
латиница или кириллица. Country/City необязательны. About Me необязательно, до 200 символов без
дополнительного списка разрешённых знаков. Проверка обязательности учитывает пробелы.

### Решение 23. Сохранение Edit Profile

`Save Changes` недоступна при pristine, invalid или `isSubmitting`; отправка идёт только через
RHF `handleSubmit`. Успех вызывает `reset(savedValues)` с ответом backend. Ошибка сохраняет
значения и dirty-состояние и показывает локальное сообщение.

### Решение 24. Значения формы Edit Profile

`EditProfileFormValues` всегда содержит `username`, `firstName`, `lastName`, `country`,
`city`, `aboutMe` как строки и `dateOfBirth: Date | null`. Необязательные строки представлены
как `''`; Avatar в форму не входит. Backend DTO заранее не создаётся.

### Решение 25. Country и City

Форма получает `countryOptions` и `cityOptionsByCountryValue` через props на основе
`SelectOption`. Значения считаются внутренними ключами UI. Пустой или изменившийся Country
очищает City; источник географических данных определяется backend-аудитом.

### Решение 26. Календарь даты рождения

Используется существующий controlled `DatePicker`. Он открывается на выбранном месяце или на
текущем месяце для `null`. Остаётся навигация по месяцам из Figma; выбор года, ручной ввод и новая
date dependency требуют отдельного решения продукта.

### Решение 27. Удаление аватара

Удаление доступно только для сохранённого аватара и подтверждается в локальном `Modal`.
`OnDeleteAvatar = () => Promise<void>`; операция не оптимистическая. Во время запроса действия и
закрытие заблокированы, ошибка сохраняет аватар и разрешает повтор.

### Решение 28. Публичные данные и сессия

Публичный SSR не зависит от `/me`. После hydration существующий `SessionProvider` показывает
элементы владельца только при точном совпадении ID. Состояние сессии не перезапрашивает публичные
данные, не меняет `baselineKey` и не скрывает страницу при ошибке сессии.

### Решение 29. Структура маршрутов поста

Канонический `posts/[postId]` размещается прямо под `(app-shell)`, а
`@modal/(.)posts/[postId]` использует существующий parallel slot. Create Post остаётся защищённым.
Оба маршрута делят загрузчик, данные и Post Details, но имеют разный способ показа и закрытия.

### Решение 30. Границы технических ошибок поста

`loadInitialPost(postId)` возвращает полные данные, `null` только для подтверждённого отсутствия
и бросает ошибку при HTTP/transport, invalid JSON, GraphQL errors или неполном ответе. Локальные
`error.tsx` используют `unstable_retry()` и не показывают детали или digest.

### Решение 31. Один GraphQL-запрос профиля

Начальный профиль загружается одним raw GraphQL POST: user, счётчики и первая
`profilePosts` page. Запрос совместим с последующим `profilePostsQuery`; `after` для первой
страницы отсутствует. Если такой ответ невозможен, это backend blocker, а не повод делать waterfall.

### Решение 32. Готовность Apollo seed

Локальная граница получает `useApolloClient()`, выполняет полный `writeQuery` в `useEffect` и
хранит `seededBaselineKey`. До совпадения ключа действует `skipToken`; запись во время render или
`useLayoutEffect` запрещена. Новый Apollo Provider или общий менеджер не создаётся.

### Решение 33. Ошибки и загрузка публичного профиля

`loadInitialProfile(userId)` возвращает полные данные, `null` только для подтверждённого
отсутствия и бросает ошибку во всех остальных сбоях. `null` использует корневой
`not-found.tsx`; локальный `error.tsx` вызывает `unstable_retry()`. `loading.tsx` и Suspense
для атомарной начальной загрузки не добавляются.

### Решение 34. Источник данных профиля после SSR

SSR и первый hydration render используют server props. После записи совпадающей версии UI может
читать свежие user/counters только из Apollo cache, без запроса из браузера. Неполный кэш не
заменяет полные серверные данные; точный Apollo primitive выбирается после проверки схемы.

### Решение 35. Навигация по публичному контенту

Все полноценные публичные Post cards в Public Home, Main, Profile и других текущих лентах/сетках
ведут через обычный Link на `/posts/[postId]`; автор — на `/profile/[authorId]`. Внутри приложения
маршрут Post может открыться через `@modal`, direct/reload остаётся публичным SSR. Ссылка покрывает
media/details surface, не весь `article`; carousel controls не запускают переход.

### Решение 36. Метаданные публичных страниц

Канонические Profile и Post получают динамические `title` и `description` из тех же данных, что
и page. Page и `generateMetadata()` используют общий `React.cache()` loader с внутренним
`cache: 'no-store'`. Перехваченный Post не делает отдельный запрос; прочие SEO-метаданные отложены.

### Решение 37. Декодирование аватара

Файл после проверки MIME/size остаётся кандидатом до cropper `onReady`; до этого Save недоступна.
`onError` освобождает object URL и сохраняет предыдущий корректный черновик либо возвращает empty
state. Callbacks старого кандидата игнорируются; export и upload на этом этапе не выполняются.

### Решение 38. Figma и повторное использование компонентов

Конкретные Figma frames задают desktop-композицию Edit Profile, Avatar, Public Profile и Post
Details. Для responsive используются существующие `AdaptiveAppShell`, Profile/Post layouts и
grids; отсутствующие значения не выдумываются. Подходящие компоненты переиспользуются, повреждённые
frames и ограничения `get_design_context` фиксируются как пробелы, а не восстанавливаются догадками.

### Решение 39. Read contract аватара

Backend подтвердил 2026-09-11: `User.avatar: File` nullable, `File.url: String!`; frontend
использует только `avatar?.url`, а при `avatar === null` показывает fallback. URL подписанный,
действует 15 минут и не является постоянным идентификатором. Каждый новый запрос `user`, `feed`
или `post` с `avatar { url }` получает свежий URL, поэтому отдельный timer/refresh-manager не нужен.
Upload/attach/replace/delete остаются backend-blocked.
